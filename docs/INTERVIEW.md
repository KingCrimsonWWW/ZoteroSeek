# 面试讲解：ZoteroSeek

> 面向「AI Agent / RAG / 工程效率」方向的简历与面试稿。数字都来自 `evals/RESULTS.md`，可直接引用。

## 1. 一句话版本

**ZoteroSeek 是一个 DeepSeek Harness 插件：把本地 Zotero 文献库用 MinerU 解析成带版式的 Markdown，做「能核对出处」的检索问答，并在侧边栏里读原文、勾选引用。** 单人两周内从 0 到可用：6 个 Agent 工具、1 个侧边栏面板、4 份评测集、37 个单测。

## 2. 简历 Bullet（按岗位取用）

**AI Agent / RAG 方向**

- 独立设计并实现 ZoteroSeek（DSH 插件，TypeScript，零第三方运行时依赖）：以 Zotero 本地 API 为只读数据源、MinerU 为 PDF→Markdown 解析器，端到端打通「入库 → 检索 → 带引用作答 → 核对」链路。
- 设计**可验证引用契约**：工具返回带稳定 `chunk_id` 的原文片段，系统提示词约束「只能引用本轮检索结果」，生成侧再用程序校验 `[^N^]` 编号并做「纠正重试 → 剥离非法标记」降级；25+14 题评测中 **citation_accuracy = 1.00、answer_rate = 1.00**。
- 在无向量库的前提下实现**跨语言检索**：122 条领域双语词表 + 两路召回（词面 / 扩展）+ 校准准入 + RRF 融合，中文提问英文文献的 `recall@5` 从 **0.07 提升到 0.79**，同语言集无回退；并用两个留出集量化了反向检索的不足，明确二期用多语 embedding 补。
- 评测驱动：自建 53 题（4 份）带 gold chunk 标注的评测集与脚本化指标（recall@5 / MRR / hit_rate / citation_accuracy / answer_rate），每次改动可复现。

**工程 / 后端方向**

- 解析链路：MinerU 云端四步异步任务（创建批次→PUT 上传→轮询→下载 zip），实现**内容寻址缓存**（sha1(pdf+参数)）与本地配额台账，重跑同一 PDF 零成本；零依赖手写 ZIP 读取器（node:zlib）。
- 分块与检索：章节栈分块（表格/公式原子块、800/100 目标）、标题/参考文献降噪、中文二元 bigram BM25（标题×3/章节×2/正文×1），281 分块单查询亚毫秒级。
- DSH 插件工程：Host 半边注册 6 个工具 + `/zotero-seek` 面板路由 + 系统提示词注入；Client 半边右侧边栏面板（React，仅用宿主模块表）、自写轻量 Markdown 渲染（表格/公式/插图）、勾选引用→写入对话。
- 交付：37 个 `node --test` 单测、`doctor/ingest/run-eval` 三个 CLI、演示脚本、架构文档，全部通过 `plugin_manager` 安装验证。

## 3. 高频追问与答法

**Q：为什么不直接用向量库？**
A：这是刻意的取舍。库是 170 篇论文、几千分块，BM25 建索引 1.4s、查询亚毫秒；词面检索可解释（能报出命中了哪些词），也没有模型下载/嵌入成本。语义召回不是没考虑，而是放在二期与现有两路 RRF 融合——并且我用留出集证明了现在缺的正是「问题里没有的数/枚举」这类语义场景。

**Q：跨语言怎么做的？为什么不直接翻译问题？**
A：词表扩展 + 两路召回 + 准入。直接把中文问题翻成英文当然可以，但需要模型调用、增加延迟且不可复现；词表是可测、可解释、零成本的一期方案。设计过「纯译文」第三路，实测没有召回增量，代码与文档里都标成未启用；数字/缩写噪声改由扩展路的覆盖率准入压制。

**Q：引用准确性怎么保证？**
A：三层。①工具返回的片段带稳定 chunk_id（全库唯一），系统提示词要求引用原样抄；②生成侧 grounded 循环校验 `[^N^]` 是否落在本轮检索编号内，不合法先带纠正提示重试一次，再失败就剥离并标注；③评测脚本统计 citation_accuracy，不靠模型自评。注意口径：citation_accuracy=1.0 只证明「没有编造引用」，内容正确性还要靠 recall 与人工抽查。

**Q：RAG 里最常见的坑是什么？你怎么绕的？**
A：三个。①**版面丢失**：Zotero 自带全文把表格拍平，所以用 MinerU 的 `content_list.json`（带 page_idx/bbox）；②**噪声块**：参考文献、页眉、版面标签都会污染检索，做了标题去重与参考文献整块丢弃（7 篇剔了 18 块）；③**引用幻觉**：见上，靠 chunk_id 契约 + 程序校验。

**Q：如果文献量涨到 1 万篇？**
A：分块与检索的分层不用改。JSON 索引会换 SQLite FTS5 + 增量写；BM25 仍可用（或换 Tantivy 类实现）；embedding 检索此时必须上，做 ANN + RRF；MinerU 解析侧要加队列与配额调度（现在是单进程串行 + 台账）。

**Q：这个项目的难点在哪？**
A：不是调模型，而是**把「不确定的生成」变成「可验证的引用」**：设计 chunk_id 契约、把校验做成产品路径的一部分、再用评测把每一步的效果量化出来。另一个难点是 DSH 插件 API 的探明——我最后是读安装包源码 + 对照一份开源插件验证出来的（笔记在 `docs/research/`）。

**Q：你踩过什么坑？**
A：MinerU 的 `page_ranges` 必须放在 `files[]` 元素里（放顶层会被忽略、按整篇计费）；MinerU 的 vlm 后端会把所有标题压成同一级，章节路径要靠标题编号自己推断；Zotero 本地 API 的 `q` 是「全 AND 子串」不是语义检索；PowerShell 的 `Invoke-WebRequest` 读 Zotero 会报 ResponseEnded（HTTP/1.0 无 Content-Length）。

## 4. 现场演示顺序（5 分钟）

见 `docs/DEMO.md`。核心三步：中文问英文文献（演示跨语言扩展）→ 侧边栏打开原文核对页码 → 跑一次评测展示数字可复现。

## 5. 可以做得更好的地方（面试官喜欢听这个）

1. **语义召回**：多语 embedding + ANN，与现有两路 RRF 融合，直接解元问题与反向检索；
2. **评测规模化**：用未参与调参的新文献做真正留出集，题量扩到 100+，标注流程半自动化（抽样脚本已在 `evals/sample-chunks.mjs`）；
3. **解析鲁棒性**：MinerU 失败重试与断点续跑、表格跨页合并；
4. **协作与权限**：面板数据面改成 DSH 的 Typert Remote（带 Peer 身份），支持多浏览器/远程访问；
5. **质量反馈闭环**：面板里给「这条引用不对」的反馈入口，沉淀成评测集。

## 6. 和参考项目的差异（如果被问到）

参考过 `dsh-zotero`（MIT）的插件形态与工具设计。ZoteroSeek 的不同在于：**MinerU 是唯一的 PDF 解析器**（结构化的表格/公式/页码是检索与核对的基础）；**引用是 chunk_id 契约 + 程序化校验**而不是单纯的编号；**跨语言检索是一等能力**并有量化评测。代码全部自写，没有搬运。
